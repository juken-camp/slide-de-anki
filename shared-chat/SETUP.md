# 第1段階の設定手順

## 必要な外部設定

1. Supabaseの新規プロジェクトを作る。既存Nekopon用のRedisは、そのまま使用する。
2. Supabase SQL Editorで `001_shared_chat.sql` を一度だけ実行する。専用スキーマを新規作成するため、同じSQLの再実行はしない。
3. AuthenticationでEmail認証を有効にする。匿名ログインは利用しない。
4. Email TemplatesのMagic Linkテンプレートに `{{ .Token }}` を含めて、メールでコードが届く設定にする。標準のリンクだけでは、この画面のコード入力と合わない。
5. AuthenticationのCustom SMTPを設定する。Supabase標準SMTPは送信先の制約があり、生徒や保護者への配信には自分のSMTPが必要。自分で管理する送信元を使い、送信サービス側のドメイン認証・送信制限も設定する。
6. Vercelに `env.example.txt` の3変数を追加する。この段階では `SHARED_CHAT_ENABLED=0` にしておく。
7. `api/shared-chat.js`、`shared-chat.html`、`shared-chat/` を追加してデプロイする。外部サービスへの契約・デプロイ自体は、この納品には含まれていない。
8. SupabaseのAuthで管理者のメールアカウントを作成・確認する。管理者アカウントのUUIDを使い、次のSQLで作成権限を付ける。

```sql
-- UUIDを実在する管理者ユーザーのIDに置き換える。
insert into shared_chat_private.creators(user_id)
values ('管理者ユーザーのUUID');

-- DB側で共有機能を有効化する。
update shared_chat_private.settings set enabled=true where id=true;
```

9. `SHARED_CHAT_ENABLED=1` に変更して再デプロイする。
10. `/shared-chat.html` を開き、管理者がログインし、グループを作成する。
11. 部屋の「参加者・管理」からリンクを発行する。招待先への送信は管理者自身が行う。
12. 別アカウントから申請→管理者が承認→2端末で投稿・削除・未読・退出後の拒否を確認する。

Supabase側はpublicをData APIの公開スキーマとして使います。`shared_chat_private` は公開スキーマに追加しないでください。ブラウザに渡るキーは公開anonキーまたは `sb_publishable_` キーだけです。`service_role` や `sb_secret_` はこの実装では不要です。

接続先は `https://プロジェクトID.supabase.co` を想定しています。セルフホストやカスタムドメインの場合、画面のCSPと接続設定の見直しが必要です。

## 確認してから試験運用する項目

- アカウントAが部屋を作成し、B・Cには作成権限がないこと。
- 招待先Bは、承認されるまで部屋の本文を読めないこと。
- 承認後はA・Bに同じ発言順・送信時刻が表示されること。
- Bの投稿でAに未読がつき、Aが末尾を読むと消えること。
- 管理者による投稿削除がBの画面にも反映されること。
- 退出処理後、Bが再取得・投稿できなくなること。
- 招待リンク無効化後、新しい人が申請できないこと。
- 従来の教材学習・個人チャット・1人用グルチャが使えること。

退出前にすでに端末で読んだ情報やスクリーンショットは回収できません。通信不能の端末から、既表示の内容を即時消去する保証もありません。

## この試験版の制限

- ログイン情報は画面のメモリにだけ保持する。再読み込み・再起動時とJWTの有効期限切れは再ログインが必要。
- 1部屋は承認待ちを含め50人まで、管理者1人の作成は10部屋まで。
- 招待は7日間・20申請まで。再発行すると旧リンクは無効になる。
- 退出・却下した人は同じ部屋に再申請できない。再参加・管理者引継ぎ・部屋の削除UIは後続実装。
- 投稿の送信制限は1人につき1分20件。招待や参加等の操作は操作別で1分10回。
- 1回に100件を表示。「以前の発言」で過去ページへ移り、「最新へ」で最新に戻る。
- 本人による編集・削除、添付画像、通報、通知設定、セッション自動更新は未実装。
- データは自動削除しない。投稿保持期間とバックアップのルールは運用前に決める。

## 一時停止

API側の環境変数だけでは、Supabaseを直接呼ぶクライアントへのDBアクセス停止にはなりません。全体を止めるときはDB側も止めます。

```sql
update shared_chat_private.settings set enabled=false where id=true;
```

この変更後は認証済み利用者からのRPCも拒否します。既存の1人用グルチャには影響しません。復帰は `enabled=true` です。

## 保守

1分単位の制限カウンタを長期に積み上げないよう、管理者のSQLまたは後続の定期保守で古い行を削除します。

```sql
delete from shared_chat_private.limits
where window_at < now() - interval '2 days';
```

監査記録は `shared_chat_private.audit` に残ります。メールアドレス・招待トークン本文・削除された投稿本文は監査記録に含めません。監査ログを閲覧する管理画面は未実装です。

## テストの再実行

```bash
cd tests
npm ci
npm test
```

追加のテスト依存はtests配下だけに入り、既存の `package.json` は変更しません。PostgreSQLのローカル検証にはPGliteを使い、Supabaseのauthスキーマを模した最小構成を作ります。実サービスのメール・JWT検証・実ネットワークの試験とは区別してください。
