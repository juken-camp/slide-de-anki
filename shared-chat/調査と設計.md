# 調査と設計

## 1. 現在の仕組み

| 役割 | 該当ファイル | ZIPで確認した動作 |
|---|---|---|
| グルチャの画面・手動送信 | `himiko.html` | `/api/himiko-chat` へmode=groupで送信。会話表示や時間差の演出をブラウザで実行 |
| 端末での会話保存 | `himiko.html` | localStorageにグループ名と直近100ターンを保存。別の端末とは共有しない |
| AI生成 | `api/himiko-chat.js` | Anthropic API。人物設定、グルチャ用プロンプト、JSON出力解析、利用制限を内包 |
| 自動会話・受信箱 | `lib/himiko-inbox.js` | Redisに端末別の状態を保存。端末トークンのハッシュが識別子。ログインアカウントではない |
| 自動会話生成 | `lib/himiko-inbox.js` | 5場面をまとめて生成し、準備済み会話から順に配信。通常10〜20分、深夜は長い間隔。発言ごとの予定時刻を保存 |
| 保存の上限 | 同上 | Redis状態は更新時から90日。保持するbatchesは直近60、既読キーは直近400。無期限の全履歴保管ではない |
| 既読・未読 | 同上、`himiko-activity.js` | 端末ごとの既読キー。未読が多いと配信を抑制する仕組み。共有部屋にはそのまま使えない |
| 人物の参加・離席等 | `lib/himiko-membership.js` | サーバーで管理するAI人物の参加状態。実際の人間の参加承認とは別 |
| 定期処理 | `api/himiko-deliver.js` | 受信箱のcron処理を呼ぶ。CRON_SECRETで保護 |
| cron登録 | `vercel.json`、`vercel-cron-example.json` | 本番設定にはcrons項目なし。別ファイルに毎分の設定例。外部スケジューラの有無はZIPでは不明 |
| 通知・バッジ | `himiko-activity.js`、`himiko-push-sw.js` | Web Push + VAPID。端末単位の購読先に配信。通知クリックは既存1人用へ戻る経路 |

つまり、サーバーで会話を生成している部分はすでにあります。新たに必要なのは、主に「保存の単位を端末から部屋へ増やすこと」と「人間のアカウントと権限管理」です。

実際に設定済みの環境変数、契約プラン、配信履歴、Redis内データは、今回のZIPには含まれていません。運用実態を確認したという意味ではありません。

## 2. 推奨構成

| 項目 | 既存1人用 | 新しい共有用 |
|---|---|---|
| 入口 | 既存の異次元グルチャ | 新しい専用ページ。後からNekoponに入口を追加 |
| 利用者識別 | 端末トークン | Supabase Authの利用者ID |
| 会話保存 | localStorage＋Redis | Supabase PostgreSQLの部屋別記録 |
| 発言順 | 各端末での演出 | 部屋ごとのseq（連番）で統一 |
| 発言時刻 | 端末表示・受信箱の予定時刻 | サーバーの時刻を全員に同じ値で配信 |
| 未読 | 端末別 | 部屋×利用者の既読位置 |
| 人間の参加承認 | なし | 管理者による承認必須 |
| AI生成 | 既存の生成処理 | 人物設定を再利用し、部屋単位のワーカーから呼ぶ（次段階） |
| 通知 | 既存の端末通知 | 利用者×端末×部屋の通知設定（次段階） |

初期は5秒ごとの取得で検証し、その後Supabase Realtime等を必要に応じて追加する方針です。Realtimeを付けても、再接続時の履歴取得と権限確認はDBを正とします。

保存はprivateスキーマ、テーブルへの直接権限はなし、RLSも有効にします。公開するRPC関数ではログイン、メール確認、参加状態、管理者権限を毎回検査します。画面でボタンを隠すだけの権限制御にはしません。

## 3. 第1段階で実装したもの

新しいページとAPI、DBスキーマを追加しました。既存ファイルには変更を加えていません。

- `shared-chat.html`：共有テストの入口。
- `shared-chat/pilot.js`、`pilot.css`：認証、部屋一覧、申請、共有投稿、管理操作。
- `api/shared-chat.js`：利用者のJWTを使う共有API。service-roleキーは使用しない。
- `shared-chat/001_shared_chat.sql`：部屋、参加状態、招待、投稿、既読位置、操作ログ、制限、RPC。
- `shared-chat/env.example.txt`：環境変数の記入例。
- `tests/`：DBアクセス制御・API境界の検証。

人間の投稿は部屋の行をロックして連番を採番し、同時送信でも同じ番号を使いません。クライアントの送信IDは部屋・利用者との組み合わせで一意なので、再送で投稿が重複しません。表示名・投稿者ID・投稿日時をクライアント側から偽装して保存することもできません。

## 4. AI共有会話を完成させるための次の改修

これは外部キーを入れるだけでは完成しません。次の実装が残っています。

1. **AI発言のデータモデル追加**：投稿種別（人間／人物／システム）、人物ID、生成ジョブID、配信待ちテーブルを加える。現在の第1段階テーブルは人間の投稿用。
2. **部屋単位の生成予約**：期限付きロックと予約IDをDBで管理。同じ部屋を複数の定期処理が同時に生成しないようにする。
3. **共通の会話生成**：現在の人物設定と構造化出力を再利用する。生成用の内部フラグはサーバーだけで設定し、利用者から渡されたフラグを信用しない。既存の受信箱は端末単位なので、そのまま共有先に転用しない。
4. **会話文脈の共通化**：部屋の履歴から、誰が話したかを保って組み立てる。複数人の発言を一人の生徒としてまとめない。1人用の個人履歴・学習記録・成績・呼ばれ方を勝手に共有しない。
5. **配信タイミング**：全員に同じ配信予定時刻を保存。未来の発言本文をブラウザに先に渡さず、配信確定時に部屋の連番を振る。途中に人間の投稿が来ても順番が矛盾しない構造にする。
6. **中断と再試行**：人間の新しい発言、AI停止、投稿削除で古くなった生成結果を予約ID・履歴世代番号で破棄する。古いワーカーが後から保存できないようにする。障害時は重複配信しない。なおAI提供元に届いたリクエストの課金まで「厳密に一度」を保証できるとは限らない。
7. **定期処理**：閉じていても配信待ちの発言を公開し、新しい会話を生成する。部屋数に応じて処理上限・再試行・失敗ログ・日次予算を設ける。
8. **通知**：共有用の通知先と購読を追加。権限・部屋の参加状態・通知設定を配信直前に確認し、退出時は以後の通知を止める。ロック画面に本文を出すかは利用者が選べる設計にする。既存SWのrootスコープと競合させず、クリック先を共有部屋へ振り分ける。
9. **管理画面**：AI停止・再開、部屋別頻度、1日の会話上限、通報、参加者再招待、管理者引継ぎを追加する。
10. **実機検証**：iPhone/PWAを含む別アカウント2〜3端末、同時送信、途中参加、バックグラウンド、長時間閉じた後、停止中の生成完了、退出直前の通知を確認する。

「ずっと誰も読まない部屋」では、保存は続けつつ生成頻度を落とす／一定期間休止するなどの運用も費用に大きく影響します。個人の未読が多いだけで部屋全体を止めないようにする必要があります。

## 5. 必要なサービスと費用

2026年11月5日に公式情報を確認。以下は米ドル、税・為替・超過利用料別。実際の契約内容は未確認です。

| サービス | 役割 | 費用の考え方 |
|---|---|---|
| 現在のVercel | HTML/APIの配信 | 既存契約を再利用可能。新しい独立アプリにすることと、新しい有料契約が必須になることは別 |
| Supabase | ログイン・部屋・発言・権限 | Freeは$0、500MBのDB。非稼働による停止あり。Proは月$25から。小規模検証後、常用時に検討 |
| メール配信/SMTP | 認証コード配信 | 自前の送信サービス設定が必要。費用はサービスと送信量次第。標準SMTPだけで保護者全員に送れると見込まない |
| Anthropic API | AI人物の会話生成 | 既存キーを再利用可能だが、共有会話の利用量が追加される。参加人数倍の生成は不要。主に部屋数×生成回数×トークン数で増える |
| 定期起動 | アプリを閉じた間の進行 | Vercel CronはHobbyが1日1回、Proは最短毎分。Proは月$20。既にProなら新たに同額が丸ごと増えるとは限らない。Supabase側のCron等も代替候補 |
| Web Push | 端末への通知 | 通知機能自体の実装が必要。サーバー処理・保存・通信の利用料に含まれる部分があり、無制限無料とはしない |

例として、Supabase ProとVercel Proをどちらも新規に使う場合、基本部分は月$45からに、メール配信・AI・超過分が加わります。これは今回の作業で契約した金額ではありません。

現行コードの既定モデルは `claude-haiku-5-5`、環境変数 `ANTHROPIC_MODEL` で変更可能です。今回確認した公式料金表では、10万トークンまでのプロンプトは入力100万トークン$0.10、出力100万トークン$0.50です。長いプロンプト、キャッシュ、別モデル等で単価が変わります。

仮に1生成あたり入力3万・出力5千トークンなら、キャッシュなしの単純計算で約$0.0055/生成、100生成で約$0.55です。このトークン量は説明用の仮定で、現在の実測ではありません。人物の名簿・履歴・生成場面数によるので、最初の部屋でusageを計測して見積もり直す必要があります。

## 6. 独立アプリとコミュニティへの展開

今回の共有データをNekoponの学習データから分離しておけば、あとから名前・ドメイン・入口を独立させやすくなります。人物設定と会話生成の共通部分を別モジュールに抜き出すと、Nekopon側と独立アプリ側で口調や史実訂正も揃えられます。

最初は家族・塾など、誰が参加者か確認できる招待制が合います。広く知らない人が参加するコミュニティへ進める際は、現在の承認だけに頼らず、通報、ミュート・ブロック、運営者対応、投稿保持期間・削除依頼窓口を組み込みます。AIは創作の人物であることを明示し、人間の参加者と混同しない表示にします。
